## What changed

The next `power.status` consumer family after the N2153 fracker slice: the Pump implementation — **rotary-pump** (consumePower 0.3f, pumpAmount 0.2f, size 2, liquidCapacity 80f) and **impulse-pump** (consumePower 1.3f, pumpAmount 0.22f, size 3, liquidCapacity 200f). The ONLY two power-consuming Pump blocks in the game (Blocks.java:2304-2320). The pump runtime (SourcePumpRuntimeState.gd) ticks only the scenario mechanical pump at PUMP_POS with efficiency hardcoded 1.0 ("consumes no power"); placed rotary/impulse pumps had NO placed-buildings driver at all — they would pump as if power.status were 1.0. N2154 is the Pump family's live read — the same proven N2145–N2153 pure-row pattern, one new file over. The scenario pump tick in SourcePumpRuntimeState.gd stays untouched.

Composition, not re-implementation: the shared efficiency machinery (`SourceBuildingEfficiencyState.update_consumption_state` + `apply_update_consumption_state`, via `update_consumption_setup_state`) already folds `{"result": ..., "is_power": true}` rows into the min efficiency — the power consumer's `ConsumePower.efficiency` is `build.power.status` (ConsumePower.java:39). N2154 does not touch it. N2154 supplies the missing pure power row + wires it into the driver.

Pure `SourceMechanicalPumpBuildState.source_mechanical_pump_power_status_row_state(frame: Dictionary, has_power_consumer: bool) -> Dictionary` — `has_power_consumer` false → `{"has_power_row": false, "row": {}}`; true → `{"has_power_row": true, "row": {"result": <live>, "is_power": true}}` where live = 1.0 if `frame.get("power_status", null)` is null else `float(frame.get("power_status"))`. The null→1.0 fold is the assembler convention (UnitAssembler.java:469, before the first graph update).

Driver wiring in `source_mechanical_pump_tick_buildings_state(game, seconds)`: iterate placed Pump buildings, bind the frame if missing, refresh frame keys (block_implementation, team_id, rules_state, cheating, enabled), and when `block.properties.has("consumePower")` and enabled and not cheating, the pure row runs through the shared machinery (`update_consumption_setup_state` + `update_consumption_state` + `apply_update_consumption_state`, should_consume=true when enabled, production_valid=true) as the only first-pass row, so `frame["efficiency"]` follows power.status and the pump accumulator fold (Pump.java:162, `float maxPump = Math.min(liquidCapacity - liquids.get(liquidDrop), amount * pumpAmount * edelta());`) follows it. Live-loop wiring: the driver is called from `simulate_factory` in SourceFactoryRuntimeState.gd right after the fracker tick.

Frame key (decided in RED): the driver uses its OWN family frame key `"source_mechanical_pump_building"` (the turret precedent — the scenario pump's key `"source_pump_building"` stays untouched, and no `source_mechanical_pump` string existed anywhere in the port before this slice). N2142's stamp/write-back only reaches frames whose meta key is in `SourcePlacedPowerGraphState.SOURCE_CONSUMER_FRAME_META_KEYS`, and that list had NO mechanical-pump key — so GREEN added `"source_mechanical_pump_building"` to that list (one line, SourcePlacedPowerGraphState.gd:140, same mechanism as the solid-pump / fracker keys).

Scope decision (decided in RED): **the Pump implementation only — rotary-pump / impulse-pump**. mechanical-pump (pumpAmount 7f/60f, liquidCapacity 20f, Blocks.java:2298-2302) has NO consumePower in Java or catalog — the driver gate `block.properties.has("consumePower")` (fracker precedent) naturally excludes it. Families considered and rejected, with reasons (catalog `content_registry.json`, verified against Java + drivers):
- BeamDrill (plasma-bore / large-plasma-bore): no BeamDrill driver exists at all — new driver needed, deferred to its own slice (N2155).
- Projectors (MendProjector, OverdriveProjector, ForceProjector, BaseShield): heal/overdrive/shield semantics, not a production-efficiency fold — separate family group, deferred.
- Payload producers (Constructor, PayloadLoader/Unloader/MassDriver, UnitCargoLoader, PayloadDeconstructor): separate family group, deferred.
- Mechanical Pump wins: 2 blocks, driver pattern exists one level up (the Fracker driver), direct `maxPump` eff fold — the smallest, safest next family in the drill/pump group already half-done.

Documented limits in the pure function's comment, same discipline as N2148–N2153: (1) power-only first pass — the liquidDrop / amount proximity (Pump.java:141-152), warmup / totalProgress (Pump.java:171-176), consTimer/consumeTime item consume (Pump.java:166-169, no-op for these pumps — neither consumes items) and dumpLiquid (Pump.java:180-182) wait for their own slices; the folded efficiency is the min over the *modeled* consumers (power only). (2) No shouldConsume gate — PumpBuild.shouldConsume() (Pump.java:155-156, `return liquidDrop != null && liquids.get(liquidDrop) < liquidCapacity - 0.01f && enabled;`) needs liquid state the tick does not track yet; the machinery runs with should_consume=true when enabled. (3) No updateTile advance — maxPump / liquids.add / warmup / totalProgress (Pump.java:161-176) wait for their own slices; the proof carries no progress keys, the maxPump fold (Pump.java:162) is what the efficiency keys prove.

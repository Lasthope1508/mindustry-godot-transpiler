# GenericCrafter warmup / liquid output / totalProgress in the live loop — N2118

Date: 2026-11-10. Batch: N2118 (single slice, SSOT slice, no emitter change). SSOT +21/+1/+4/+8 → 11077 / 1569 / 1480 / 2751; audit `totalSourceFunctions` stays 1335. Second C06 slice (factory→core leg).

## What changed

After N2117 (progress increase + craft), three statements of `GenericCrafterBuild.updateTile()` (GenericCrafter.java:235-266) were still unwired: the warmup approach, the continuous liquid output loop, and totalProgress. N2118 wires all three through the live loop, in Java order.

- `SourceFactoryBuildState.source_factory_warmup_target_state(block)` implements `GenericCrafterBuild.warmupTarget()` (GenericCrafter.java:287-289): returns 1f. The HeatCrafter override (`Mathf.clamp(heat / heatRequirement)`, HeatCrafter.java:70-72) is deferred — the frame carries no heat state yet, so a heat crafter takes the GenericCrafter default. A null block has no target (0.0).
- `SourceFactoryBuildState.source_factory_warmup_state(warmup, target, warmup_speed, seconds)` implements the `Mathf.approachDelta` step (GenericCrafter.java:239, efficiency above zero; GenericCrafter.java:253, efficiency zero): step = `Time.delta * warmupSpeed`, moved = warmup + clamp(target − warmup, −step, step). `Time.delta` is in seconds. warmupSpeed is the block's own, else the class default 0.019f (GenericCrafter.java:45); the only initializer override in Blocks.java is the blast drill (a Drill, not a factory).
- `SourceFactoryBuildState.source_factory_liquid_output_state(block, liquids, liquid_ids, efficiency, seconds, time_scale)` implements the continuous liquid output half of `updateTile()` (GenericCrafter.java:241-246): `inc = getProgressIncrease(1f)` — the GenericCrafter override at base time 1f, so a full output liquid scales inc to zero through the same headroom scaling N2117 registered — then each output liquid is handled once per tick, `handleLiquid(this, output.liquid, Math.min(output.amount * inc, liquidCapacity - liquids.get(output.liquid)))`, capped at the remaining capacity so the module never overfills. `handleLiquid` is `liquids.add` (BuildingComp.java:872-874); `LiquidModule.add` (LiquidModule.java:110-115) is `liquids[liquid.id] += amount` with `current` set to the liquid. A block with no output liquids outputs nothing (inc 0); a null block outputs nothing. The tick only calls this while efficiency is above zero.
- `SourceFactoryBuildState.source_factory_total_progress_state(total_progress, warmup, seconds)` implements `totalProgress += warmup * Time.delta` (GenericCrafter.java:259-260; `Time.delta` is in seconds, not ticks). It runs every tick, outside the efficiency branch — a factory at efficiency zero still banks the warmup it has left as it cools.
- The tick driver `source_factory_tick_buildings_state(game, seconds)` (extended in place, still N2110) now approaches warmup, handles the output liquids and banks totalProgress every tick — totalProgress before the craft check, the Java order (GenericCrafter.java:259-264) — and crafts when progress reaches 1.0. A driver-order fix moved the craft check after the totalProgress step to match Java; the check is behavior-neutral (craft does not read totalProgress).
- New owner constants `PORT_GAME_SOURCE_FACTORY_BUILD_WARMUP_TARGET_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_WARMUP_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_LIQUID_OUTPUT_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_TOTAL_PROGRESS_STATE` in `SourceRuntimeOwnerGameplayRegistry.gd`.
- No emitter change this slice: the registry already carries `outputLiquids`, `liquidCapacity` and `craftTime` (N2113/N2117). The `content_registry_blocks` shard mirror was rebuilt anyway (the N2114 lesson); all five `production_*` / registry shards on disk equal a fresh build.

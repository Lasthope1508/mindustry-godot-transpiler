## What changed

N2104 captured the class init's `ConsumeLiquidFilter` into the registry (one `consumeLiquid` descriptor per ammo liquid at `liquidConsumed` 1/60) and N2105 wired the tick to read `ammoTypes` from the registry, but nothing consumed the liquid yet: a placed sublimate kept its ozone and cyanogen forever. N2106 binds a `RuntimeConsumer` actor per `consumeLiquid` row into the live-loop tick and runs it through `BuildingComp.updateConsumption`'s second pass, so the placed turret actually consumes its ammo liquid each tick.

- `SourceContinuousLiquidTurretBuildState.source_bind_consumer_state(frame, block, catalog, amounts)` — binds one `RuntimeConsumer` actor per bound `consumeLiquid` row (the drill model, N2097/N2100), each removing its own liquid at `amount * edelta * multiplier` through the N2101 cost-multiplier callback. Actors are bound once — a frame that already carries them binds nothing — and a block without `consumeLiquid` rows binds none. Returns `{"bound", "consumers", "rows"}`.
- `SourceContinuousLiquidTurretBuildState.source_consumed_liquid_state(frame, liquids, liquid_names_by_id)` — `ConsumeLiquidFilter.getConsumed` (ConsumeLiquidFilter.java): the current liquid when the filter admits it and its amount is positive, else the first content liquid the filter admits with amount left; null when none has any. The filter is `ammoTypes.containsKey` (ContinuousLiquidTurret.java:40). Returns `{"consumed_liquid", "consumed_index"}` (liquid id, -1 when none).
- `SourceContinuousLiquidTurretBuildState.source_tick_buildings_state(game, seconds)` — gains the frame delta (the live loop passes `simulate_factory`'s `delta` in seconds; `SourceFactoryRuntimeState.simulate_factory` updated to pass it). Each tick the driver: refreshes the frame keys via N2102's wiring; sets `team_id`, `rules_state` and `cheating` from the live rules (the drill pattern, N2097/N2099) so the multiplier callback and the cheating gate read what Java reads (`b.team`, `state.rules`); binds the consumers; runs `updateConsumption` (BuildingComp.java:1943-2004) — first pass takes the minimum efficiency of the non-optional consumers, second pass updates each update consumer when `shouldConsume && productionValid` and efficiency > 0, where `shouldConsume` is enabled && the hysteresis value from the previous tick; only the consumed liquid's actor counts, so a second ammo liquid at rest neither blocks efficiency nor drains; then updates `activated` (ContinuousLiquidTurret.java:71-81: `super.updateTile()` runs first, so a turret that just received liquid starts consuming on the next tick, not this one). The live flow cache stays unbound (the tick asserts `liquids["flow"] == null`) — the drill's lifecycle slice owns it.

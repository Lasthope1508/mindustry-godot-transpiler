# GenericCrafter progress + craft() in the live loop — N2117

Date: 2026-11-10. Batch: N2117 (single slice, **hybrid: SSOT slice + registry emitter change**). SSOT +38/+1/+5/+10 → 11056 / 1568 / 1476 / 2743; audit `totalSourceFunctions` stays 1335. First C06 slice (factory→core leg).

## What changed

The tick driver only refreshed consumption before this slice: a placed GenericCrafter-family building never gained progress and never crafted. N2117 wires the production half of `GenericCrafterBuild.updateTile()` (GenericCrafter.java:235-266) into the live loop.

- `SourceFactoryBuildState.source_factory_progress_increase_state(craft_time, efficiency, seconds, time_scale)` implements `BuildingComp.getProgressIncrease` (BuildingComp.java:1203-1205): `1f / baseTime * edelta()`, with `edelta()` = efficiency × `delta()` (BuildingComp.java:1927-1929) and `delta()` = `Time.delta * timeScale` (BuildingComp.java:1922-1924); the port edelta is seconds × 60, so one tick at efficiency 1.0 is edelta 1.0 and a smelter gains 1/40. A zero craft time or zero efficiency gains nothing.
- `SourceFactoryBuildState.source_factory_crafter_progress_increase_state(block, liquids, liquid_ids, efficiency, seconds, time_scale)` implements the `GenericCrafterBuild.getProgressIncrease` override (GenericCrafter.java:266-285): `ignoreLiquidFullness` takes the base increase; otherwise the increase scales by `(liquidCapacity - held) / (amount * edelta())` per output liquid, `dumpExtraLiquid` taking `min(max, 1f)` and `!dumpExtraLiquid` taking the minimum scaling. A block with no output liquids (silicon smelter, graphite press) takes the base increase unchanged.
- `SourceFactoryBuildState.source_factory_consume_state(frame, consumers, rows)` implements `BuildingComp.consume()` (BuildingComp.java:1911-1915): it triggers every consumer, but only the item rows remove anything (`ConsumeItems.trigger`, ConsumeItems.java:45-48, removes `round(stack.amount * multiplier)`); liquid rows are skipped here. `SourceConsumeItemsState.RuntimeConsumer.trigger(build)` is the new trigger body.
- `SourceFactoryBuildState.source_factory_offload_state(game, frame, cell, block, item)` implements `BuildingComp.offload(Item)` (BuildingComp.java:1000-1016): `produced(item, 1)`, then the cdump-order proximity loop — the first neighbor that `acceptItem`s and `canDump`s takes the item, otherwise the building keeps it.
- `SourceFactoryBuildState.source_factory_craft_state(game, frame, cell, block)` implements `GenericCrafterBuild.craft()` (GenericCrafter.java:301-315): `consume()`; each output item is offloaded once per amount; `progress %= 1f`. The consumers and rows are the frame's own bound actors and rows (N2112 binds them, N2116 reinitializes them), so craft takes no separate actor list — the 4-parameter form. A null block crafts nothing. Cheating does not gate craft-time consumption in Java: `consume()` has no cheat check (only per-tick `updateConsumption` early-returns), so a cheating factory still pays its items at the craft while its per-tick liquid drain is frozen.
- The tick driver `source_factory_tick_buildings_state(game, seconds)` (extended in place, still N2110) now advances `frame["progress"]` by the GenericCrafter override when efficiency is above zero and crafts when progress reaches 1.0.
- Emitter: `mindustry_port/content_registry.py` captures `craftTime` for GenericCrafter/AttributeCrafter/HeatCrafter/HeatProducer (the block initializer's own assignment, else the class default 80, GenericCrafter.java:40). **31 blocks carry craftTime** (silicon smelter 40.0, graphite press 90.0, cryofluid mixer 120.0). The `content_registry_blocks` shard mirror was rebuilt.
- New owner constants `PORT_GAME_SOURCE_FACTORY_BUILD_PROGRESS_INCREASE_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_CRAFTER_PROGRESS_INCREASE_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_CONSUME_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_OFFLOAD_STATE`, `PORT_GAME_SOURCE_FACTORY_BUILD_CRAFT_STATE` in `SourceRuntimeOwnerGameplayRegistry.gd`.

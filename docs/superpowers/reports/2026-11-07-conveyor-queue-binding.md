One design note: Java's `add(o)` loop starts at `Math.max(o + 1, len)`, so inserting at the end (`o == len`) performs one stale copy beyond the new length; the GDScript version skips the shift in that case (the appended slot is the insertion point, to be filled by handleItem) — same visible queue, no out-of-bounds write. Invalid indices (`add` with `index > len`, `remove` with `index >= len`) fail closed with reason `invalid_index` and the queue unchanged.

## Ownership and actual API boundary

`SourceConveyorRuntimeState` gains `source_conveyor_queue_add_state` (N2053), `source_conveyor_queue_remove_state` (N2054) and `source_conveyor_queue_scan_state` (N2055).

- **N2053 add.** `source_conveyor_queue_add_state(ids, xs, ys, len, index) -> Dictionary`. Shifts the three parallel arrays right from the insertion index and increments len; the slot at `index` keeps its old value (duplicated) for the caller (handleItem) to overwrite with the inserted item and its x/y. Result keys: `ids_after, xs_after, ys_after, len_before, len_after, shifted, reason` (shifted, invalid_index).
- **N2054 remove.** `source_conveyor_queue_remove_state(ids, xs, ys, len, index) -> Dictionary`. Shifts the three parallel arrays left from the removal index, drops the stale tail and decrements len. Same result keys.
- **N2055 scan.** `source_conveyor_queue_scan_state(ys, passed_by_index) -> Dictionary`. The updateTile mid/minitem scan over the ys array, iterating from the last item down: `mid = i - 1` for every `i > 0` with `ys[i] > 0.5` (so the final value comes from the smallest such i), and `minitem` is the smallest y among items that did not pass (starting from 1.0). Result keys: `mid, minitem`. The `passed_by_index` input models the `pass(ids[i])` branch of the same loop; per-frame movement itself stays with the path-progress runtime.

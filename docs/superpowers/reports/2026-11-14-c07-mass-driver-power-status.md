## What changed

The next `power.status` consumer family after the N2170 wall-crafter slice: the MassDriver implementation family — ONE def, **mass-driver** (consumePower 1.75f, Blocks.java:2173; size 3, itemCapacity 120, reload 200f, range 440f, Blocks.java:2167-2174). MassDriver extends Block (MassDriver.java:27, `public class MassDriver extends Block{`); its build extends Building and implements RotBlock (MassDriver.java:115, `public class MassDriverBuild extends Building implements RotBlock{`). Catalog confirms implementation MassDriver + consumePower 1.75 + hasPower true + consumesPower true + powerUsage 1.75 (source_modules/content_registry_blocks.json, mass-driver entry). Blocks.java def is the source of truth, see Exact exprs. There is no large-mass-driver def in this upstream version (no largeMassDriver in Blocks.java; the catalog carries mass-driver only), so the single def is the whole family.

The mass driver has NO driver at all — it extends Block, not a factory or crafter, so no existing driver matches it, and no frame key exists for it, so the N2142 stamp never reaches a mass-driver frame. Its updateTile no-power skip (MassDriver.java:169, `if(efficiency <= 0f){`) gates on efficiency, so a mass driver with no power would keep rotating and firing as if power.status were 1.0. N2171 is the mass driver's live read — the same proven N2145–N2170 pure-row pattern, on the N2170 wall-crafter precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring.

MassDriverBuild has NO shouldConsume override, so the BuildingComp default (BuildingComp.java:755-757, `return enabled;`) applies — the machinery runs with should_consume=true when enabled (the MendProjector suppression precedent).

Scope decision (verified this run): the candidate order after WallCrafter listed Incinerator next, but Incinerator needs NO dedicated slice — N2146 already did the adjacent-factory power.status live read for the whole Separator/Incinerator/WallCrafter/SingleBlockProducer family (ledger N2146 godot_owner SourceAdjacentFactoryBuildState.source_adjacent_factory_power_status_row_state; proof GREEN 8/8 keys, matches:true). The adjacent driver folds the pure power row for every adjacent-family block with a power consumer, its frame key `"source_adjacent_factory_building"` IS in SOURCE_CONSUMER_FRAME_META_KEYS, and the driver IS wired into simulate_factory — so the N2142 stamp already reaches an incinerator frame and its efficiency already folds live power.status. N2171 is MassDriver, the first candidate with genuinely no driver. (Lesson for the next scope: check the driver before scoping a family.)

New file `godot-mindustry/src/game/SourceMassDriverBuildState.gd`, class_name SourceMassDriverBuildState, with `SOURCE_MASS_DRIVER_BUILD_IMPLEMENTATIONS := ["MassDriver"]` and frame meta key `"source_mass_driver_building"`:

- Driver `source_mass_driver_tick_buildings_state(game, seconds)` (mirrors the wall-crafter driver: iterate placed buildings, match implementation, bind frame, tick frame, when `block.properties.has("consumePower")` and enabled and not cheating fold the pure row via `source_building_efficiency_state.update_consumption_state(true, ...)` with has_consumers=true — the power consumer counts toward hasConsumers, Block.java:1449 — and apply it; no consumer actors, no production tick, no updateTile advance).

New frame key `"source_mass_driver_building"` added to `SourcePlacedPowerGraphState.SOURCE_CONSUMER_FRAME_META_KEYS` so the N2142 graph stamp/write-back finds the mass-driver frame. Wiring in `SourceFactoryRuntimeState.simulate_factory`: preload `source_mass_driver_build_state` + call `source_mass_driver_tick_buildings_state(game, delta)` (next to the wall-crafter call).

Documented limits in the pure function's comment, same discipline as N2148–N2170: (1) power-only first pass — the mass driver's power consumer is static (consumePower 1.75f, Blocks.java:2173), so the folded efficiency is the min over the *modeled* consumers (power only). (2) shouldConsume default applies — MassDriverBuild has no shouldConsume override, so the BuildingComp default (`return enabled;`, BuildingComp.java:755-757) applies; the machinery runs with should_consume=true when enabled (the MendProjector suppression precedent). (3) No updateTile advance — link/state-machine / reloadCounter / waitingShooters / rotation align / fire / dumpAccumulate (MassDriver.java:133-221) wait for their own slices; the proof carries no link/state/reload/fire keys, the no-power skip (MassDriver.java:169) is what the efficiency keys prove. (4) No link/config / fire / handlePayload / sense / draw / read-write / acceptItem rows — see DEFERRED. (5) Single def — no large-mass-driver def in this upstream version, so the same driver covers the whole family.

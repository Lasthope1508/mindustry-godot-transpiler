**Family split — phase-conveyor only:** the ItemBridge family splits into TWO defs with TWO implementations — phase-conveyor carries `consumePower(0.30f)` (Blocks.java:2125, catalog `consumePower: 0.3`) + `hasPower` true, `consumesPower` true, implementation `ItemBridge`; bridge-conveyor carries NO consumePower (Blocks.java:2106-2115, no consumePower call), `hasPower` false, NO `consumePower` property in the catalog (implementation `BufferedItemBridge`). This slice covers **phase-conveyor only**. The driver's implementation list holds `ItemBridge` only — `BufferedItemBridge` must NOT match, because it has no power consumer; the exact-string implementation check enforces the split. Catalog quirk respected: bridge-conveyor lists `consumesPower: true` despite `hasPower: false` and no `consumePower` property — the plain radar gate `block.properties.has("consumePower")` correctly includes phase-conveyor and excludes bridge-conveyor. `BufferedItemBridge extends ItemBridge` (BufferedItemBridge.java:9) overrides only transport/dump: `hasPower = false;` (:18), `bufferCapacity = 50` (class default; def overrides to 14, Blocks.java:2113), `speed = 74f` (def, Blocks.java:2112). Its `updateTransport` polls an ItemBuffer instead of the edelta loop — bridge-conveyor transport does NOT depend on power.status, so excluding it from the power driver is correct, not a gap.

The efficiency coupling that makes this slice matter: `updateTransport` charges by edelta (`transportCounter += edelta();`, ItemBridge.java:356) and moves one item per `transportTime` (2f for phase-conveyor, Blocks.java:2119) — so a phase-conveyor with no power never advances its transport counter (edelta() = efficiency * delta(), BuildingComp.java:1928) and never moves items across the bridge, while the port without this slice would behave as if power.status were 1.0. `warmup = Mathf.approachDelta(warmup, efficiency, 1f / 30f);` (ItemBridge.java:345) also follows the folded efficiency when a valid link exists; without a link `warmup = 0f` (:337). `draw()` uses `float warmup = hasPower ? this.warmup : 1f;` (ItemBridge.java:387) — the bridge-conveyor (hasPower false) always draws warmup 1f, another reason the two defs must not share one driver row. N2178 is the item bridge's live read — the same proven N2145–N2177 pure-row pattern, on the N2173 radar precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring.

**Power is STATIC here** — unlike RepairTurret's conditional draw: `consumePower(0.30f)` registers a plain ConsumePower, so the catalog `consumePower: 0.3` is present and the plain radar gate `block.properties.has("consumePower")` works — no RepairTurret-style `or consumesPower` adaptation needed. The pure row is the same ConsumePower read (`return build.power.status;`, ConsumePower.java:39).

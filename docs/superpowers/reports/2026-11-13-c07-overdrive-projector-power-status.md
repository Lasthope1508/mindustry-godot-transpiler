N2157 is the OverdriveProjector family's live read — the same proven N2145–N2156 pure-row pattern, one new file over. Second projector family: the deferred list in the N2156 handoff named remaining projectors (Overdrive/Force/BaseShield/Regen) as the next group after MendProjector.

OverdriveProjector extends Block, NOT a drill or factory, so it cannot reuse an existing frame key; it gets its own family frame key (the mechanical-pump / beam-drill / mend-projector precedent).

Composition, not re-implementation: the shared efficiency machinery (`SourceBuildingEfficiencyState.update_consumption_state` + `apply_update_consumption_state`, via `update_consumption_setup_state`) already folds `{"result": ..., "is_power": true}` rows into the min efficiency — the power consumer's `ConsumePower.efficiency` is `build.power.status` (ConsumePower.java:39). N2157 does not touch it. N2157 supplies the missing pure power row + wires it into the driver. The port already has OverdriveProjector display/runtime state (SourceOverdriveProjectorRuntimeState.gd: `runtime_step_state` lerps smooth_efficiency and heat toward 1.0, and `real_boost(overdrive_projector, phase_heat, efficiency)` multiplies by efficiency with default 1.0 — the boost fold already consumes efficiency) — the missing piece was the live power.status → efficiency driver, which is exactly this slice.

Pure `SourceOverdriveProjectorBuildState.source_overdrive_projector_power_status_row_state(frame: Dictionary, has_power_consumer: bool) -> Dictionary` — `has_power_consumer` false → `{"has_power_row": false, "row": {}}`; true → `{"has_power_row": true, "row": {"result": <live>, "is_power": true}}` where live = 1.0 if `frame.get("power_status", null)` is null else `float(frame.get("power_status"))`. The null→1.0 fold is the assembler convention (UnitAssembler.java:469, before the first graph update).

Driver wiring in `source_overdrive_projector_tick_buildings_state(game, seconds)`: iterate placed OverdriveProjector buildings, bind the frame if missing, refresh frame keys (block_implementation, team_id, rules_state, cheating, enabled), and when `block.properties.has("consumePower")` and enabled and not cheating, the pure row runs through the shared machinery (`update_consumption_setup_state` + `update_consumption_state` + `apply_update_consumption_state`, should_consume=true when enabled, production_valid=true) as the only first-pass row, so `frame["efficiency"]` follows power.status and the real-boost fold (OverdriveProjector.java:124, `return (speedBoost + phaseHeat * speedBoostPhase) * efficiency;`) follows it. Live-loop wiring: the driver is called from `simulate_factory` in SourceFactoryRuntimeState.gd next to the mend-projector tick.

Frame key (decided in RED): the driver uses its OWN family frame key `"source_overdrive_projector_building"` (verified no collision: grep finds no `source_overdrive_projector_building` anywhere in the port — the existing `SourceOverdriveProjector*` files use per-cell state dicts, not this meta key). N2142's stamp/write-back only reaches frames whose meta key is in `SourcePlacedPowerGraphState.SOURCE_CONSUMER_FRAME_META_KEYS`, and that list had NO overdrive-projector key — so GREEN added `"source_overdrive_projector_building"` to that list (one line, SourcePlacedPowerGraphState.gd:140, same mechanism as the mend-projector key).

Scope decision (decided in RED): **the OverdriveProjector implementation only — overdrive-projector / overdrive-dome**. Families considered and rejected, with reasons (catalog `content_registry.json`, verified against Java + drivers):
- Remaining projectors (ForceProjector force-projector 4f, BaseShield shield-projector 5f, RegenProjector regen-projector 1f): separate projector slices, deferred after this one.
- Payload producers (Constructor, PayloadLoader/Unloader/MassDriver, UnitCargoLoader, PayloadDeconstructor): separate family group, deferred.

Documented limits in the pure function's comment, same discipline as N2148–N2156: (1) power-only first pass — the phaseFabric (overdrive-projector) and phaseFabric+silicon (overdrive-dome) booster item rows wait for their own slices; the folded efficiency is the min over the *modeled* consumers (power only). (2) No shouldConsume gate — OverdriveBuild has no shouldConsume override, so the default (BuildingComp.java:755-757, `return enabled;`) applies; the machinery runs with should_consume=true when enabled. (3) No updateTile advance — smoothEfficiency / heat / charge / phaseHeat / useProgress / boost application (OverdriveProjector.java:97-120) wait for their own slices; the proof carries no progress/boost keys, the real-boost fold (OverdriveProjector.java:124) is what the efficiency keys prove. (4) No useProgress consume() rows — useTime 400f / dome 300f (OverdriveProjector.java:117-120) wait for their own slice; the dome's hasBoost=false (Blocks.java:1960) means its phaseHeat stays 0, also part of the updateTile advance.

## What changed

The next `power.status` consumer family after the N2174 repair-turret slice: the ShieldWall implementation family — a SINGLE def, **shielded-wall** (`consumePower(3f / 60f)` = 0.05, Blocks.java:1905; shieldHealth 900f, breakCooldown 60f×10f, regenSpeed 2f, ShieldWall.java:15-17; chanceDeflect 8f, health 260 * wallHealthMultiplier * 4, armor 15f, size 2, Blocks.java:1903-1916). ShieldWall extends Wall (ShieldWall.java:14, `public class ShieldWall extends Wall{`); its build extends WallBuild (ShieldWall.java:43, `public class ShieldWallBuild extends WallBuild{`). Catalog confirms implementation ShieldWall + hasPower true + consumesPower true + consumePower 0.05 + outputsPower false + powerUsage 0.05 + connectedPower true (source_modules/content_registry_blocks.json, shielded-wall entry). Blocks.java defs are the source of truth, see Exact exprs in the handoff.

The shield wall had NO driver at all — no `SourceShieldWall*` file exists in godot-mindustry/src/game, no `ShieldWall` mention in any `godot-mindustry/src/game/*.gd`, no `ShieldWall` entry in any `SOURCE_*_IMPLEMENTATIONS` list (the base-shield driver covers `BaseShield` only, `SourceBaseShieldBuildState.gd:30`; the turret driver covers turrets only; the adjacent driver covers Separator/Incinerator/WallCrafter/SingleBlockProducer only). No `Wall` implementation list exists either — `Wall` itself has no driver, and it would not match the `ShieldWall` implementation string anyway. No frame key existed for it, so the N2142 stamp never reached a shield-wall frame. The Incinerator lesson was applied: the candidate was checked for an existing driver before scoping.

The efficiency coupling that makes this slice matter: `updateTile` regens the shield by edelta (`shield = Mathf.clamp(shield + regenSpeed * edelta(), 0f, shieldHealth);`, ShieldWall.java:80), and `broken()` is `return breakTimer > 0 || !canConsume();` (ShieldWall.java:92) with `canConsume()` returning `potentialEfficiency > 0` (BuildingComp.java:1917-1919) — so a shield wall with no power is broken, its shield absorbs nothing, and its shield never regens, while the port without this slice would behave as if power.status were 1.0. `potentialEfficiency` is assigned the folded efficiency before the `if(!update)` zeroing (BuildingComp.java:1988-1994), so the broken() coupling follows the folded value. N2175 is the shield wall's live read — the same proven N2145–N2174 pure-row pattern, on the N2173 radar precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring.

**Power is STATIC here** — unlike RepairTurret's conditional draw: `consumePower(3f / 60f)` registers a plain ConsumePower, so the catalog `consumePower: 0.05` is present and the plain radar gate `block.properties.has("consumePower")` works — no RepairTurret-style `or consumesPower` adaptation needed. The pure row is the same ConsumePower read (`return build.power.status;`, ConsumePower.java:39).

**No shouldConsume override** — neither ShieldWall.java nor Wall.java overrides it, so the BuildingComp default applies (`return enabled;`, BuildingComp.java:755-757). Same as Radar (N2173): the machinery runs with should_consume=true when enabled (the MendProjector suppression precedent). No open point for RED — unlike RepairTurret, there is no target-gated override to decide.

New file `godot-mindustry/src/game/SourceShieldWallBuildState.gd`, class_name SourceShieldWallBuildState, with `SOURCE_SHIELD_WALL_BUILD_IMPLEMENTATIONS := ["ShieldWall"]` and frame meta key `"source_shield_wall_building"`:

## What changed

The next `power.status` consumer family after the N2171 mass-driver slice: the LaunchPad implementation family — TWO defs sharing one implementation, **launch-pad** (consumePower 4f, Blocks.java:6797; size 3, itemCapacity 100, launchTime 60f * 20, Blocks.java:6790-6797) and **advanced-launch-pad** (consumePower 8f, Blocks.java:6809; size 4, itemCapacity 100, launchTime 60f * 30, liquidCapacity 40f, drawLiquid oil, consumeLiquid oil 9f/60f, Blocks.java:6800-6809). LaunchPad extends Block (LaunchPad.java:30, `public class LaunchPad extends Block{`); its build extends Building (LaunchPad.java:83, `public class LaunchPadBuild extends Building{`). Catalog confirms implementation LaunchPad + consumePower 4.0/8.0 + hasPower true + consumesPower true + powerUsage 4.0/8.0 (source_modules/content_registry_blocks.json, launch-pad / advanced-launch-pad entries). Blocks.java defs are the source of truth, see Exact exprs.

The launch pad has NO driver at all — no `SourceLaunchPad*` file exists in godot-mindustry/src/game, it extends Block, not a factory or crafter, so no existing driver matches it, and no frame key exists for it, so the N2142 stamp never reaches a launch-pad frame. Its updateTile launch gate (LaunchPad.java:146, `if((launchCounter += edelta()) >= launchTime && items.total() >= itemCapacity){`) advances launchCounter by edelta() (BuildingComp.java:1927-1929, `return efficiency * delta();`), so a launch pad with no power would never launch — its launchCounter would sit frozen as if power.status were 1.0. N2172 is the launch pad's live read — the same proven N2145–N2171 pure-row pattern, on the N2171 mass-driver precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring. The same driver covers both defs via the catalog consumePower.

LaunchPadBuild HAS a shouldConsume override (LaunchPad.java:92-95, `return launchCounter < launchTime;`) — the gate waits for its own slice (needs launchCounter state the tick does not track yet); the machinery runs with should_consume=true when enabled (the MendProjector suppression precedent), the same discipline as the WallCrafter/Separator deferred shouldConsume gates.

New frame key `"source_launch_pad_building"` added to `SourcePlacedPowerGraphState.SOURCE_CONSUMER_FRAME_META_KEYS` so the N2142 graph stamp/write-back finds the launch-pad frame. Documented limits in the pure function's comment, same discipline as N2148–N2171: (1) power-only first pass — the launch pad's power consumer is static (consumePower 4f/8f, Blocks.java:6797/6809), so the folded efficiency is the min over the *modeled* consumers (power only). (2) shouldConsume override deferred — LaunchPadBuild HAS a shouldConsume override (`return launchCounter < launchTime;`, LaunchPad.java:92-95); the gate needs launchCounter state the tick does not track yet, so the machinery runs with should_consume=true when enabled (the MendProjector suppression precedent). (3) No updateTile advance — launchCounter / launchSound / LaunchPayload / Fx.launchPod / items.clear (LaunchPad.java:143-161) wait for their own slices; the proof carries no launch/counter/payload keys, the launch gate (LaunchPad.java:146) is what the efficiency keys prove. (4) No liquid consumer row — advanced-launch-pad consumes oil 9f/60f (Blocks.java:6808); see DEFERRED. (5) Two defs, one driver — launch-pad + advanced-launch-pad share the LaunchPad implementation, so the same driver covers the whole family; the advanced def waits for its own verification slice.

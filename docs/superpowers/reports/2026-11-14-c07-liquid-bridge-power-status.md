**Family split — phase-conduit only:** the LiquidBridge family splits into TWO defs with ONE implementation — phase-conduit carries `consumePower(0.30f)` (Blocks.java:2396, catalog `consumePower: 0.3`) + `hasPower` true, `consumesPower` true, implementation `LiquidBridge`; bridge-conduit carries NO consumePower (Blocks.java:2374-2383, `hasPower = false;` at :2380), `hasPower` false in Java, NO `consumePower` property in the catalog (implementation `LiquidBridge`). The plain radar gate `block.properties.has("consumePower")` correctly includes phase-conduit and excludes bridge-conduit. **reinforced-bridge-conduit is a DIFFERENT class, out of scope:** `reinforcedBridgeConduit = new DirectionLiquidBridge("reinforced-bridge-conduit")` (Blocks.java:2432), `hasPower = false;`, no consumePower. The efficiency coupling that makes this slice matter: the warmup gate (`if(warmup >= 0.25f){`, LiquidBridge.java:23) blocks ALL liquid movement until warmup reaches 0.25f, and warmup itself follows the folded efficiency through the inherited ItemBridge updateTile (`warmup = Mathf.approachDelta(warmup, efficiency, 1f / 30f);`, ItemBridge.java:345) — so a phase-conduit with no power never warms up and never moves liquid, while the port without this slice would behave as if power.status were 1.0. `draw()` uses `float warmup = hasPower ? this.warmup : 1f;` (ItemBridge.java:387) — the bridge-conduit (hasPower false) always draws warmup 1f, another reason the two defs must not share one driver row. bridge-conduit transport does NOT depend on power.status: with no power consumer its efficiency stays 1.0 when enabled, so warmup still reaches 0.25f and liquid still moves — excluding it from the power driver is correct, not a gap. N2179 is the liquid bridge's live read — the same proven N2145–N2178 pure-row pattern, on the N2173 radar precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring.

## Scope (decided at scoping)

- Family: the RepairTurret implementation family — TWO defs, **repair-point** (powerUse 1f, Blocks.java:6391; repairSpeed 0.45f, repairRadius 60f, Blocks.java:6388-6389) and **repair-turret** (powerUse 5f, Blocks.java:6402; size 2, repairSpeed 3f, repairRadius 145f, Blocks.java:6398-6401; acceptCoolant true, coolantUse 0.16f, coolantMultiplier 1.6f, Blocks.java:6404-6406). RepairTurret extends Block (RepairTurret.java:25, `public class RepairTurret extends Block{`); its build extends Building (RepairTurret.java:153, `public class RepairPointBuild extends Building implements Ranged, RotBlock{`). Catalog confirms implementation RepairTurret + hasPower true + consumesPower true for both defs, with consumePower None (source_modules/content_registry_blocks.json, repair-point / repair-turret entries) — None because the power draw is CONDITIONAL, not absent: see below. Blocks.java defs are the source of truth, see Exact exprs.
- Why: the repair turret has NO driver at all — no `SourceRepairTurret*` file exists in godot-mindustry/src/game, it extends Block, not a factory or crafter, so no existing driver matches it (the turret driver's line-28 comment mentions RepairTurret explicitly but does NOT list it — its list is ItemTurret/LiquidTurret/PowerTurret/LaserTurret/ContinuousTurret only), and no frame key exists for it, so the N2142 stamp never reaches a repair-turret frame. Its updateTile heal advance (RepairTurret.java:207, `target.heal(repairSpeed * strength * edelta() * multiplier);`) heals by edelta() (BuildingComp.java:1927-1929, `return efficiency * delta();`), so a repair turret with no power would never heal — its target's health would sit frozen as if power.status were 1.0. N2174 is the repair turret's live read — the same proven N2145–N2173 pure-row pattern, on the N2173 radar precedent (new family file + own driver + own frame key + simulate_factory wiring): one new pure function on a new state file + a driver fold + a new frame key + the wiring. The same driver covers both defs via the catalog implementation (the conditional consumer is registered per def through powerUse, not consumePower).
- **Power is CONDITIONAL, not static** — the one way this family differs from Radar/LaunchPad: `consumePowerCond(powerUse, (RepairPointBuild entity) -> entity.target != null);` (RepairTurret.java:89, init()). ConsumePowerCondition only draws when its condition holds: `return consume.get(entity) ? usage : 0f;` (ConsumePowerCondition.java:17). Catalog consumePower None is CORRECT for this family — it records no static consumePower def, and the power draw is 1f / 5f only while a target is locked. The pure row is still the same ConsumePower read (`return build.power.status;`, ConsumePower.java:39) — ConsumePowerCondition does not override efficiency(), so the row folds power.status exactly like the static case.
- **shouldConsume override EXISTS** — unlike Radar (no override, BuildingComp default applies), RepairPointBuild overrides it: `return target != null && enabled;` (RepairTurret.java:222). And updateConsumption forces efficiency to zero when the gate is false: `boolean update = shouldConsume() && productionValid();` (BuildingComp.java:1960) + `if(!update){` (BuildingComp.java:1992, efficiency = optionalEfficiency = 0f). So the driver MUST apply the shouldConsume gate: with no target, Java efficiency is 0 even though the graph status would read 1.0 (requestedPower 0 draws nothing). This is the MendProjector suppression precedent, but explicit and target-driven here — see Design, open point (target frame input).
- The updateTile heal advance (target re-acquire every 20 ticks, RepairTurret.java:216-219; heal + rotation slerp, RepairTurret.java:203-210; strength lerp, RepairTurret.java:212) waits for its own slice — the proof carries no heal/strength/rotation/target keys; the heal advance (RepairTurret.java:207) is what the efficiency keys prove.
- Out of scope for this slice: the updateTile heal / target-acquire / rotation / strength rows, draw / drawSelect / drawPlace / icons rows, read/write (rotation) rows, status() override, range() accessor, the coolant optional consumer (repair-turret only: ConsumeCoolant, acceptCoolant, coolantUse 0.16f, coolantMultiplier 1.6f — optional pass, BuildingComp.java:1979-1981), the powerUse defs as display stats — all deferred, see register script DEFERRED (to be derived from the N2173 script at RED).
